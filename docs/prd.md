## 1. 개요

### 1.1 한 줄 요약
고객사 통화 녹취 음성 파일을 입력받아 **STT → 생성형 AI(UiPath GenAI / ChatGPT) 분석 → UiPath RPA 후처리**를 거쳐, 5대 문의 유형 분류·요약·조치 내역을 자동 정리하고 **① 내부 보고용 엑셀 대시보드**와 **② 실시간 웹 시각화 대시보드**를 동시에 산출하는 AI 비서.

### 1.2 배경 (AS-IS)
고객사 전화 응대 담당자 3명이 상담 종료 후 이력을 수작업으로 관리하고 있음.

| 문제 | 내용 |
|---|---|
| 수기 기록 의존 | 통화 후 개인 기억에 의존해 복기·기록 → 세부 문의·핵심 맥락 누락 위험 |
| 반복 후처리 공수 | 매 통화마다 [유형 분류 → 질문 요약 → 조치 내역 정리 → 엑셀 입력] 반복 |
| 데이터 활용 한계 | 엑셀 Row 데이터로만 누적 → 유형별 추이·불만 현황 파악 및 보고에 추가 시간 소요 |

### 1.3 목표 (TO-BE)
| 목표 | 설명 |
|---|---|
| 후처리 업무 제로화 | 음성 파일만으로 5대 유형 분류, 핵심 요약, 조치 내역 자동 추출 |
| 데이터 정확도·일관성 | 담당자별 기록 편차 제거, 표준 포맷으로 DB·엑셀 자동 적재 |
| 이원화 결과물 자동 산출 | 내부 보고용 엑셀 + 실시간 모니터링용 웹 대시보드 동시 제공 |

### 1.4 성공 지표 (KPI) **[가정 — 목표치 합의 필요]**
| 지표 | 목표 |
|---|---|
| 통화 1건당 후처리 소요 시간 | 수작업 대비 80% 이상 절감 |
| 5대 유형 분류 정확도 | 검증 세트 기준 90% 이상 |
| STT 문자 오류율(CER) | 상용 STT 수준(클로바노트 대비 동등 수준) |
| 파이프라인 처리 성공률 | 업로드 건 대비 95% 이상 자동 완료 (나머지는 예외 큐로 수동 처리) |
| 녹취 1건 처리 시간 | 업로드 후 5분 이내 대시보드 반영 |

## 3. 범위

### 3.1 In Scope
- 음성 파일(.wav, .mp3 등) 수집 — 입력 위치는 클라우드 폴더(Google Drive `inbox/` **[가정]**) 하나. 사용자가 직접 올리거나, 웹에 올리면 서버가 같은 폴더에 대신 올리고, UiPath 로봇이 이를 직접 감지한다. 상세: `input_flow.md`
- 화자 분리가 적용된 STT (상담원 / 고객)
- GenAI 기반 5대 유형 분류, 요약, 조치 내역·개체명 JSON 추출
- 개인정보(PII) 마스킹
- DB 적재 및 Raw 데이터 CRUD
- 엑셀 대시보드형 보고서 자동 생성
- 웹 시각화 대시보드 (업로드, 모니터링, 통계, 다운로드)
- 레거시 시스템(CRM/ERP) 입력 자동화 (RPA)
- UiPath Orchestrator 운영 (Time Trigger, Dispatcher/Performer, Queue/예외 처리)

### 3.2 Out of Scope
- **챗봇** (상담 조회·업무 처리용) — 개발하지 않음
- **로그인 / 인증 기능** — 개발 공수 절감을 위해 제외 (접근 제어는 네트워크 수준으로 대체 **[가정]**)
- 실시간 통화 중 스트리밍 분석 (통화 종료 후 녹취 파일 기반 배치 처리만 대상)
- 전화 교환기(PBX) 직접 연동 **[가정]**
- 백엔드 서버의 Orchestrator API 호출(Job 실행·Queue 등록) — 처리 시작은 RPA가 주도 (`input_flow.md`)

## 4. 시스템 아키텍처 (End-to-End 파이프라인)

```
[Step 1 Input]              [Step 2 STT]            [Step 3 GenAI]              [Step 4 RPA]              [Step 5 Output]
 녹취 파일 적재         →   화자 분리 텍스트 변환 →  5대 유형 분류·요약·      →  엑셀 양식 기입,          →  ① 엑셀 대시보드 보고서
 (클라우드 inbox/ ←     (상용 STT + 전처리)     조치내역 JSON 추출·PII마스킹  CRM/ERP 입력, 예외 처리      ② 웹 시각화 대시보드
  사용자 직접 / 웹→서버)
        │
        ▼ Dispatcher 로봇: 클라우드 폴더 확인(Time Trigger) → 서버 등록 → Queue 추가
        ▼ Performer 로봇: Step 2~4 수행, 단계별 결과를 Backend API로 적재
                    Backend API 서버 (DB / 음성 사본 저장소 / 조회·통계·엑셀 다운로드)
```

처리 시작의 주도권은 RPA에 있으며, 백엔드는 로봇이 보내는 등록·결과를 받아 저장·제공한다. 상세 흐름은 `input_flow.md` 참조.

### 4.1 구성 요소
| 구성 요소 | 기술 | 역할 |
|---|---|---|
| 입력 채널 | 클라우드 폴더 Google Drive(공유 드라이브) `inbox/` **[가정]**. 웹 업로드는 서버가 Drive API로 `inbox/`에 업로드 | 녹취 파일 수집 |
| STT | 상용 STT API (예: 네이버 CLOVA Speech) **[결정 필요]** + 전처리 + GenAI 교정 | 화자 분리 전사 |
| GenAI | UiPath.GenAI.Activities / ChatGPT | 분류·요약·JSON 추출·PII 마스킹 |
| RPA | UiPath Studio, Orchestrator(Time Trigger, Queue) | 파일 감지(Dispatcher), 처리 오케스트레이션(Performer), 엑셀·레거시 입력 |
| Backend | FastAPI (`research.md` 권장안) | 로봇 등록·결과 적재 API, DB, 음성 사본 저장, 조회·통계 |
| DB | PostgreSQL (`research.md` 권장안) | 상담 원문·분석 결과·처리 상태 저장 |
| Frontend | 웹 대시보드 | 시각화, 조회, CRUD, 다운로드 |

## 5. 기능 요구사항

우선순위: **P0** = MVP 필수, **P1** = 1차 릴리스, **P2** = 선택/후순위

### 5.1 음성 데이터 인입 (Input)
| ID | 요구사항 | 우선순위 |
|---|---|---|
| IN-01 | 클라우드 폴더 `inbox/`에 음성 파일이 적재되면 Dispatcher 로봇이 주기적(Time Trigger)으로 감지하여 처리를 시작한다 | P0 |
| IN-02 | 지원 포맷: .wav, .mp3 (기타 포맷 추가 여부 **[결정 필요]**). 미지원 파일은 `failed/`로 이동 | P0 |
| IN-03 | 웹 대시보드에서 음성 파일을 업로드할 수 있다 (다중 파일). 서버는 파일을 클라우드 `inbox/`에 대신 업로드만 하고 처리는 IN-01 경로를 따른다 | P1 |
| IN-04 | Dispatcher는 STT 시작 전에 반드시 백엔드에 등록(메타데이터·해시·음성 사본)하며, 백엔드는 음성 사본을 자체 저장소에 보관한다 | P0 |
| IN-05 | 담당자(3명 중 1인), 고객사, 통화 일시 메타데이터를 파일명 규칙에서 자동 추출한다. 추출 실패 시 빈 값으로 등록하고 "메타데이터 확인 필요"로 표시하며, 처리(STT·분석)는 계속 진행한다 **[파일명 규칙 결정 필요]** | P0 |
| IN-06 | 중복 파일(동일 해시)은 백엔드 등록 시 감지하여 처리하지 않는다 | P1 |
| IN-07 | 파일은 `inbox/ → processing/ → done/ · failed/` 폴더 이동으로 처리 상태를 표시하고, 이동 선점으로 동시 처리를 막는다 | P0 |
| IN-08 | 사용자는 브라우저 또는 Google Drive 데스크톱 앱으로 `inbox/`에 직접 올릴 수 있다. 로컬 폴더는 개발·테스트 용도로만 사용한다 | P0 |

### 5.2 음성 텍스트 변환 (STT)
| ID | 요구사항 | 우선순위 |
|---|---|---|
| STT-01 | 녹취 음성을 텍스트 스크립트로 변환한다 | P0 |
| STT-02 | 화자 분리(Diarization)로 상담원/고객 발화를 구분한다 | P0 |
| STT-03 | 통화 녹취 잡음 전처리를 적용한다 | P1 |
| STT-04 | 도메인 특화 용어 사전(키워드 Boost/Prompt)을 적용한다 | P1 |
| STT-05 | GenAI 후처리로 오인식 문장을 교정한다 (원문 전사본은 별도 보존) | P1 |
| STT-06 | 품질 기준: 단순 오픈소스(기본 Whisper) 대비 우수, 클로바노트 수준 확보를 목표로 비교 검증한다 | P0 |

### 5.3 생성형 AI 분석
| ID | 요구사항 | 우선순위 |
|---|---|---|
| AI-01 | 상담 1건을 5대 유형 중 하나로 분류한다: **질의 / 불만 / 건의 / 교육 내용 / 기타 문의** (복수 유형 허용 여부 **[결정 필요]**) | P0 |
| AI-02 | 고객 질문 요지를 요약한다 | P0 |
| AI-03 | 담당자 조치 내역을 구조화하여 추출한다 | P0 |
| AI-04 | 개체명(고객사명, 제품/서비스명, 일정, 후속 조치 필요 여부 등)을 추출한다 | P1 |
| AI-05 | 결과는 사전 정의된 JSON 스키마(§6.2)로 출력하며, 스키마 검증 실패 시 재시도 후 예외 큐로 이관한다 | P0 |
| AI-06 | 주민번호·전화번호·계좌번호 등 PII를 마스킹한 뒤 저장·외부 전송한다 | P0 |
| AI-07 | 분류 신뢰도(confidence)를 함께 산출하고, 임계값 미만은 "검토 필요"로 표시한다 | P1 |
| AI-08 | 프롬프트 세트를 버전 관리한다 | P1 |

### 5.4 RPA 데이터 처리 및 적재
| ID | 요구사항 | 우선순위 |
|---|---|---|
| RPA-01 | 추출된 JSON을 DB에 저장한다 (Backend API 경유) | P0 |
| RPA-02 | 내부 보고용 엑셀 양식에 자동 기입한다 | P0 |

## 6. 데이터 요구사항

### 6.1 DB 엔터티 (초안)
| 테이블 | 주요 컬럼 |
|---|---|
| `call_record` | id, source_type, source_ref, object_key, file_hash, agent_name, client_company, call_datetime, metadata_incomplete, duration_sec, status, status_changed_at, retry_count, queue_item_id, deleted_at, created_at, updated_at |
| `transcript` | id, call_id, segments(JSON: 화자별 발화·타임스탬프), corrected_text, stt_engine |
| `analysis` | id, call_id, category, confidence, question_summary, action_summary, entities(JSON), raw_json, prompt_version, needs_review |
| `processing_log` | id, call_id, step, status, message, orchestrator_job_id, created_at |
| `edit_history` | id, call_id, field, before, after, editor, edited_at (P2) |

`status`: `REGISTERED` → `QUEUED` → `STT_DONE` → `STORED` / `NEEDS_REVIEW`, 실패 시 `FAILED` → (재처리 요청) `RETRY_REQUESTED` → `QUEUED`. 일정 시간 이상 멈춘(정체) 건도 재처리 요청 가능

`metadata_incomplete`: 파일명에서 메타데이터를 추출하지 못한 건 표시. 처리 상태와 별개이며 웹에서 보정하면 해제 (상세: `architecture.md` §5)
